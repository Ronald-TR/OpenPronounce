# Phase 0 Spike — Phone recognition in the browser

**Status update:** Phase 1 (full comparison pipeline port + component parity),
Phase 2 (reference TTS, acoustic term and the complete score) and Phase 3
(production UI, model manager, recording and PWA) are done. The headless smoke
test now runs the REAL app end-to-end: fixture scored 99/100 in the browser.

**Goal:** validate the hypothesis that OpenPronounce's core model
(`wav2vec2-lv-60-espeak-cv-ft`, phone recognizer) can run client-side with
acceptable latency and output parity with the Python pipeline.

**Verdict: GO.** All go criteria passed.

## Setup

- Model: [`onnx-community/wav2vec2-lv-60-espeak-cv-ft-ONNX`](https://huggingface.co/onnx-community/wav2vec2-lv-60-espeak-cv-ft-ONNX) (int8/q8, 318 MB), loaded with transformers.js 3.8 (ONNX Runtime Web), inside a Web Worker.
- UI: Vite + TypeScript + Tailwind v4 (self-hosted, no CDN — required for COEP).
- Page served with COOP/COEP headers (`web/public/_headers`) → `crossOriginIsolated: true` → WASM threads enabled.
- Fixtures: 3 gTTS samples (1.8 s / 2.7 s / 4.8 s), expected phones generated by the Python pipeline (`web/scripts/generate_fixtures.py`).

## Results

### Parity vs Python (fp32 torch, `openpronounce.phones`)

| Fixture | Audio | Phones | Match | Notes |
|---|---|---|---|---|
| en-hello | 1.8 s | 9 | 8/9 | `ʌ`→`ɛ` in "Hello": borderline argmax flip (int8 drift) |
| en-coffee | 2.7 s | 21 | 21/21 | exact |
| en-weather | 4.8 s | 40 | 40/40 | exact |
| **Total** | | **70** | **69 (98.6 %)** | |

The single divergence is a substitution of a near phone on one word, exactly the
kind of borderline case the phase-4 calibration step is designed for.

### Latency (MacBook, 11 cores)

| Runtime | 1.8 s audio | 2.7 s audio | 4.8 s audio | vs real time |
|---|---|---|---|---|
| Node, onnxruntime-node (CPU, q8) | 0.10 s | 0.15 s | 0.25 s | ~19× |
| **Chromium headless, WASM threads (q8)** | — | **0.84 s** | — | **~3.2×** |

The 5-second-clip go criterion (≤ 15 s on WASM) is met with a wide margin
(extrapolated ~1.5 s). CTC decode is negligible (≤ 2 ms).

### Resources

- Download: 318 MB (q8); q4 variant available at 242 MB; fp16 632 MB for WebGPU.
- Memory: Node RSS ~1.2 GB after load+inference; browser JS heap stays small
  (model weights live in the WASM heap).
- transformers.js caches model files in the browser Cache API after first load.

## Go criteria (from the plan)

| Criterion | Target | Measured | Status |
|---|---|---|---|
| Phone parity vs Python | ≥ 95 % | 98.6 % | ✅ |
| Inference, 5 s clip, WASM | ≤ 15 s | ~1.5 s (extrapolated) | ✅ |

## Pending / next phase

# Phase 1 — Comparison pipeline port (done)

The rest of `phones.py` now runs in TypeScript with **component-level parity**
against fixtures generated from the Python pipeline
(`web/scripts/generate_fixtures_phase1.py`):

| Component | TS module | Parity |
|---|---|---|
| Levenshtein distance + opcodes | `core/levenshtein.ts` | exact — including rapidfuzz's tie-breaking |
| FastDTW (0.3.4, distances + paths) | `core/dtw.ts` | exact |
| G2P via espeak-ng WASM (`phonemizer` npm) | `core/g2p.ts` | exact after normalization (6/6 fixture texts) |
| Alignment, near-phone costs, plausibility, per-phone reports | `core/compare.ts` | exact — errors, confidences, per-phone reports |
| `compare_phones` end-to-end | `core/compare.ts` | exact on 4 cases (incl. a mismatch case with 5 flagged words) |

Notable findings:

- **rapidfuzz opcode tie-breaking**: reproduced with a forward walk over the
  suffix-distance matrix preferring **insert > replace > delete** (discovered
  empirically against fixtures + hand-built discriminating cases).
- The espeak-ng **WASM build differs slightly** from the system espeak (e.g.
  `ɔː` vs `ɔ`), but after the shared normalization both converge to identical
  phone sequences on all fixture texts.
- G2P runs in the browser too (rendered live in the spike UI; covered by the
  headless smoke test).

`npx vitest run` passes 5/5 (4 ungated + 1 model test gated behind
`OPENPRONOUNCE_PARITY=1`).

# Phase 2 — Reference TTS, acoustic term and the full score (done)

The complete Python score now runs client-side:

| Piece | Implementation | Result |
|---|---|---|
| Reference TTS | piper WASM (`@diffusionstudio/vits-web`), voice `en_US-lessac-medium` (~63 MB, OPFS-cached) | synthesizes in-browser |
| Acoustic encoder | `facebook/wav2vec2-large-960h` encoder exported to ONNX by `scripts/export_embedding_model.py`, int8 (355 MB, self-hosted under `web/public/models/`) | matches torch distances within int8 drift |
| Acoustic DTW | ported fastdtw over 1024-dim frames | 0.02 s for 2.7 s audio in the browser |
| Word term | `onnx-community/wav2vec2-base-960h-ONNX` q8 (~95 MB) in the worker | transcript of the fixture: "i would like a cup of coffee please" |
| Score | `core/score.ts` port of `compute_pronunciation_score` | exact parity with Python on fixture grids |

**End-to-end (headless Chromium, WASM q8):** the coffee fixture scores
**95.05 / 100** against its own text (acoustic 7.49, 0 phone errors,
0 word errors) — SMOKE TEST PASSED.

Calibration notes (provisional until the phase-4 speechocean762 rerun):

- torch fp32 on the same pairs: gTTS-vs-piper same sentence 5.45, wrong
  sentence 14.31 — consistent with the shipped `acoustic_good=6.0` / `bad=15`.
- int8 encoder drift pushes the browser "good" pair to ~7.5: the score band
  still behaves (native-like reading ⇒ 95+), but phase 4 should recalibrate
  `ACOUSTIC_GOOD` against the quantized encoder.

Total browser download (English, first visit): ~318 MB (phones) + 355 MB
(encoder) + ~95 MB (ASR) + ~63 MB (piper voice) ≈ **830 MB**, all cached by
the browser (Cache API + OPFS) after the first load.

Remaining phase-2 known gaps: the embeddings model is quantized uniformly
(no per-channel calibration), WebGPU still untested (headless has no WebGPU),
and mobile is out of scope for the MVP.

# Phase 3 — Production UI, model manager and PWA (done)

`web/index.html` is now the real app (the spike lives on at `/spike.html` as a
diagnostics page):

- **Practice flow** ported from the server app: sentence + example chips,
  record button, microphone picker, auto-stop toggle (`AudioRecorder` ported
  to `src/app/recorder.ts` with `setDeviceId` + `setSilenceDetection`),
  upload + drag-drop, loading/error/result views.
- **Result view**: score ring, verdict, flagged word chips, per-word phone
  detail (expected vs heard with per-phone confidences), heard phones,
  transcript and a score breakdown line.
- **Model manager**: what is downloaded and its sizes, `navigator.storage.estimate`
  usage, and a "delete downloaded models" action (Cache API + piper OPFS flush).
- **PWA**: web manifest + service worker (workbox precache of the app shell,
  ~24 MB incl. the ORT runtimes; the ~830 MB of models stay in the libraries'
  own caches). COOP/COEP survive offline navigation because the SW caches the
  responses with their original headers.
- **Architecture**: all inference (phone recognizer, ASR, acoustic encoder)
  lives in ONE worker behind a promise-based RPC (`WorkerClient`); G2P and
  piper run on the main thread. Moving the encoder out of the main thread into
  the worker fixed a memory/thread-pressure hang (a second ORT instance + two
  growing WASM heaps was too much for headless Chromium).

End-to-end smoke on the production app (`npm run test:browser`): upload the
coffee fixture → analyze → **99/100** (acoustic 6.28, 0 phone errors, 0 word
errors, correct transcript).

Bugs found and fixed along the way: worker responses nested `requestId` inside
the payload (RPC never resolved), a buffer detached twice via postMessage
(empty input to the encoder), and the smoke test reading the score mid
count-up animation.

Still pending: visemes + Chart.js charts in the result view (all data is
available client-side), WebGPU trial, phase-4 calibration, phase-5 deploy.

# Phase 4 — Calibration against speechocean762 (done)

The full benchmark sample was re-scored through the browser's models:

- Sample: the same 500 utterances as the Python benchmark (seed 0, stratified,
  `benchmarks/results/speechocean762-v0.3.csv`).
- Harness: `web/scripts/export_calibration_set.py` (audio + manifest) →
  `npm run calibrate` (Node, quantized encoder, same ONNX the browser runs) →
  `web/scripts/analyze_calibration.py` (correlations + grid search + CV).

## Results

| Pipeline | Spearman vs human total |
|---|---:|
| Python (torch fp32), shipped constants | 0.6518 |
| **Browser (ONNX int8), shipped constants** | **0.6478** |
| Browser, grid-searched constants (0.7/0.3/0, GOOD 8, BAD 18) | 0.6850 (held-out CV 0.6839) |

- int8 distance drift: +0.93 on average, distance correlation 0.94 with torch.
- The grid search reproduces the Python finding documented in `speech.py`:
  heavier acoustic weights correlate slightly better but stop punishing a
  wrong sentence. **Decision: keep the shipped constants** (0.3/0.4/0.3,
  GOOD 6 / BAD 15) — the browser pipeline loses only 0.004 Spearman and keeps
  the deliberate wrong-sentence penalty.
- No threshold recalibration needed for the phone confidences: the phone/word
  components are bit-identical to Python (phase-1 parity), so the word-level
  precision/recall behaviour carries over.

## WebGPU

Headless Chromium and headless Chrome (channel: `chrome`) expose no
`navigator.gpu` on this machine — the measurement must be manual:

1. `cd web && npm run build && npm run preview`
2. Open http://localhost:4173/spike.html in Chrome/Edge.
3. Pick device `webgpu`, quantization `fp16` (or `q4f16`), load, analyze the
   fixtures, and compare the timings against the wasm/q8 row in the table above.
4. The encoder (`web/public/models/...`) has no fp16 export yet; run
   `scripts/export_embedding_model.py` with `torch.float16` if it becomes the
   bottleneck.

# Deploy (test) — GitHub Pages

`.github/workflows/deploy-pages.yml` builds `web/` on every push to `main`
(typecheck + unit tests + `VITE_BASE=/<repo>/ npm run build`) and publishes
`web/dist` through GitHub Pages (actions/deploy-pages).

**Repo setup (once):** Settings → Pages → Source: **GitHub Actions**.

Pages specifics handled here:

- **Subpath**: `vite.config.ts` reads `VITE_BASE` (defaults to `/`); all asset,
  manifest, viseme and encoder paths are base-relative.
- **COOP/COEP**: GitHub Pages cannot set headers, so `coi-serviceworker`
  (vendored, MIT, in `web/public/`) adds them client-side and reloads the page
  once — WASM threads keep working. The PWA service worker registration is
  disabled (`injectRegister: false`) so it never competes for the scope.
- **No self-hosted models in this test deploy**: the acoustic encoder lives in
  `web/public/models/` (gitignored) and will 404 on Pages. The app degrades
  gracefully — the score drops the acoustic term and renormalizes over phones
  (4/7) + words (3/7); the breakdown line shows `acoustic n/a`. The other
  models (phone recognizer, ASR, piper voice) download from the HF CDN. For a
  production deploy, publish the encoder ONNX to a CDN/HF repo and point
  `ENCODER_PATH`/`env.localModelPath` at it.

## Known issue: browser word-transcription regression (open)

Since some point after phase 4, the word-transcription model
(wav2vec2-base-960h int8) outputs **all-blank logits in the browser**,
zeroing the word term of the score. Extensively diagnosed:

- identical model bytes (sha256 = HF original), identical normalized input
- Node (onnxruntime-node, cpu) transcribes the same fixture correctly —
  `I|WOULD|LIKE|A|CUP|OF|COFFEE|PLEASE`
- browser (onnxruntime-web, wasm): 135/135 frames argmax to blank, in every
  dtype (q8/fp16), binary (JSEP/non-JSEP), thread count, env configuration,
  model source (HF/local/S3) and load order; enhancement is not involved
- the phone recognizer (wav2vec2-lv-60-espeak, also int8) works in the same
  worker/session — the regression is specific to this model on ORT-web

Mitigation shipped: an empty transcript drops the word term and renormalizes
the score over acoustic + phones (the breakdown shows `words n/a`).

Next steps to investigate: pin/compare an older onnxruntime-web build,
inspect the JSEP loader's int8 handling for base-960h, or switch the word
term to a browser-native SpeechRecognition pass (privacy trade-off).
